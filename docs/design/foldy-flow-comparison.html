01 / 지금은 어떻게 동작하나

도형은 도형대로,
문제 글은 별도로 읽습니다.

사용자가 문제 칸을 고르면 브라우저가 도형 네모를 추천합니다. 사용자가 확인한 도형을 잘라 각각 서버로 보내고, 문제 글은 따로 읽어 마지막에 결과에 붙입니다.

중요한 차이
문제 글을 나중에 결과에 붙이는 것은, 도형을 해석할 때 그 문맥을 참고하는 것과 다릅니다. 현재 도형 해석기는 잘린 도형 사진을 주로 보므로, 평면 종이접기인지 입체 전개도인지 판단할 문장이 빠질 수 있습니다.
API 경로의 코드 기본값

그림과 글에 다른 모델

도형: gemini-3.5-flash
문제 글: gemini-3.5-flash-lite

이름은 현재 코드 기준입니다. 실제 사용 가능 여부·설정은 실행 시 확인해야 합니다.

팀 테스트용 agy 경로

CLI를 통한 모델 실행

도형 기본값: gemini-4-argon-low
글 기본값: gemini-3.8-flash-low

환경변수로 변경 가능합니다. 현재 활성 엔진은 이 문서에서 단정하지 않습니다. agy는 팀 테스트 경로입니다.

같은 입력 바이트는 실행 중 메모리 캐시에서 재사용할 수 있습니다. agy에는 미리 실행·지연 시 추가 요청도 있습니다. 따라서 아래 호출 수 비교는 캐시 미적중·재시도 없는 경우의 기본 구조를 뜻합니다.

02 / Traditional CV의 원리

“무슨 도형인지”보다
“어두운 색칠이 어디 있는지”를 찾습니다.

현재 알고리즘은 학습 모델이 아닙니다. 종이보다 어둡고 검은 글자보다 밝은 영역을 찾고, 작은 얼룩을 지운 뒤 연결된 덩어리를 네모로 감쌉니다.

제안에서도 유지할 부분

빠른 후보 네모 추천. 별도 신경망 가중치를 다운로드하지 않습니다.

후보는 최종 정답이 아닙니다. 못 찾거나 잘못 찾으면 수정할 수 있어야 합니다.

데이터로 개선할 부분

60문제 중 개발용 사진으로 밝기 기준·그림자 제거·라벨 여백 등을 조정합니다.

예시를 코드에 넣으면 자동으로 학습되는 구조가 아닙니다. 실패를 보고 규칙을 고치는 작업입니다.

“퓨샷”은 Gemini 쪽에 적용합니다.
CV는 데이터로 규칙을 조정하고, Gemini에는 대표 문제와 바른 판정 예시를 보여줍니다. 별도 학생 모델을 학습시키는 지식 증류는 첫 실험에 포함하지 않습니다.
03 / 바꾸려는 흐름

문맥과 그림을 함께 보고,
한 번에 판별과 구조 추출을 시도합니다.

CV의 빠른 위치 추천은 남깁니다. 서버에는 문제 문장과 보기 관계가 보이는 문제 영역, 그리고 필요한 도형 확대 이미지를 함께 보냅니다.

사진에서 궁금한 문제 선택

문장과 그림이 함께 들어오게 감쌉니다. 문제집 전체를 매번 AI에 보내는 방식은 아닙니다.

↓

CV로 후보 네모 추천

사용자가 확인·수정할 수 있습니다. 빠진 도형이 있을 가능성을 숨기지 않습니다.

문제 전체는 문맥용, 확대 이미지는 작은 숫자·라벨용입니다. 보기 번호와 각 이미지의 대응을 유지합니다.

② 지원 가능 / 미지원 / 정보 부족인지

↓

검증한 뒤 기존 뷰어로 표현

정보가 충분하면 3D로 구성합니다. 부족하면 확인을 요청하고, 미지원이면 이유를 안내합니다.

“분류만 빠르게”로는 3D가 완성되지 않습니다.
“정육면체 전개도입니다”라는 답 외에 6개 면의 위치·크기·글자 등이 필요합니다. Flash-Lite가 유형 판별과 구조 추출을 모두 충분히 잘하는지가 이번 실험의 핵심입니다.

첫 후보는 gemini-3.5-flash-lite입니다. “mini latest” 대신 공식 모델 ID를 기록합니다. 모든 문제를 한 번에 처리하는 것이 충분히 정확하고 저렴한지는 실험으로 판단합니다. 공식 모델 목록

한 번에 모두 읽으면 항상 더 싸고 빠른가요?

아닙니다. 문제 전체와 확대 사진을 함께 보내면 입력 토큰이 늘고, 여러 도형을 출력하면 출력도 길어집니다. 호출 수 감소가 전체 비용·지연 감소로 이어지는지는 측정해야 합니다. 복잡한 문제에서 정확도가 떨어지면 처리 범위를 줄이거나 사용자 확인, 필요한 경우에만 더 강한 모델을 쓰는 방식을 비교합니다.

현재 문제 칸 + 도형 2개를 읽는 일반 경로는 기본적으로 도형 해석 2회와 문제 글 읽기 1회입니다. 제안은 기본 1회로 묶는 실험입니다. 캐시·재시도·agy 추가 요청이 있으면 실제 호출 수는 달라집니다.

04 / 어떤 문제인지 구분하는 원리

그림 모양과 문제 문장을
같이 해석합니다.

같은 사각형도 입체의 한 면일 수 있고, 접는 종이일 수 있습니다. 아래 버튼은 설명용 예시를 바꿉니다.

지원 후보

직육면체의 한 면 ABCD에 대각선을 그었습니다.

입체의 면이라는 문맥을 읽습니다. 전체 입체의 치수와 면 대응까지 있어야 정확히 구성할 수 있습니다.

“올바르게 접히지 않는다”는 이유로 버리지 않습니다.
전개도가 아닌 보기를 고르는 문제에서는 잘못된 배치도 학습 대상입니다. 사진 배치를 그대로 보존하고, 임의로 올바른 전개도로 바꾸지 않습니다.

입력 전에는 범위 안내

“현재는 정육면체·직육면체의 그림과 전개도를 읽을 수 있어요.”

학생이 정확한 전문 용어를 알아야만 사용할 수 있게 만들지는 않습니다.

입력 뒤에는 세 가지 대응

지원: 정보가 충분하면 표시.
미지원: 이유와 가능한 범위 안내.
정보 부족: 문제 영역 확대·확인 요청.

05 / 3D에는 어떤 모델을 쓰나

3D 생성 AI를 추가하지 않습니다.
기존 기하 코드가 그립니다.

Gemini가 만드는 것은 3D 파일이 아니라 도형을 설명하는 데이터입니다. three.js는 그 데이터를 바탕으로 면·모서리·라벨을 화면에 그립니다.

구성 요소역할
ShapeScene도형 종류·치수·전개도·라벨을 전달하는 데이터 형식
gridNet.ts사진에서 읽은 전개도 면 배치를 뷰어가 쓸 면 구조로 변환
polyhedra.ts지원하는 다면체의 면·연결 관계와 기하 관련 처리
faceTree.ts연결된 면들의 회전 계층을 만들고 펼침 값을 적용
ThreeViewer.tsxthree.js 장면·카메라·재질·상호작용으로 표시
“즉시 모델링”의 조건
필요한 데이터가 도착하면 별도의 생성형 AI 호출 없이 그릴 수 있습니다. 하지만 사진 업로드부터 AI 응답·장면 구성까지의 전체 시간이 즉각적이라는 뜻은 아닙니다. 실제 기기에서 측정해야 합니다.
06 / 적당량의 데이터를 어떻게 쓰나

첫 예산은 60문제.
요청마다 넣는 예시는 0개와 4개를 비교합니다.

40문제

개발용

CV 규칙 조정, 문제 판별 지시 개선, 대표 퓨샷 선정에 사용합니다.

20문제

최종 확인용

다른 교재·원본 문제 묶음으로 분리합니다. 조정 중에는 보지 않습니다.

겨냥도 / 올바른 전개도 / 잘못된 전개도 / 평면 종이접기 / 지원 밖 입체·기타 / 문맥 부족·혼합 문제를 각 10개씩 구성하는 초안입니다. 같은 문제의 회전·밝기 변형은 같은 묶음에 둡니다.

서로 다른 두 종류의 “데이터 반영”

CV: 개발용 사진에서 실패를 보고 규칙·임곗값을 고칩니다. 사진 40장을 서비스 코드에 넣고 돌리는 것이 아닙니다.

Gemini: 대표 예시 4개를 프롬프트에 넣는 방식을 시험합니다. 예시가 없는 방식과 비교해 성능 이득이 작으면 예시를 뺍니다. 이미지 예시는 입력 비용까지 계산합니다.

비교안구성확인할 것
A · 현재현재 CV + 현재 서버 인식정확도·호출·대기·사용자 수정의 기준선
B · 최소 구성CV + Flash-Lite 통합 호출, 퓨샷 0개추가 예시 없이도 충분한가?
C · 소수 예시CV + Flash-Lite 통합 호출, 퓨샷 4개입력 비용 증가보다 정확도 개선이 큰가?

모델·호출 통합·CV 수정이 동시에 바뀌면 원인을 알기 어렵습니다. 먼저 같은 CV 출력과 같은 문제 입력으로 B/C를 비교하고, CV 조정 효과는 별도 비교합니다. 60문제는 첫 의사결정 예산이며 정확도를 보장하는 표본 수가 아닙니다.

60문제를 모두 여러 모델로 심사해야 하나요?

아닙니다. 첫 단계는 사람이 문제 유형·지원 여부·도형 네모를 확인합니다. 지원하는 문제는 최종 출력의 치수·면 배치·라벨도 원본과 비교해야 합니다. 필요할 때 모델 심사를 보조로 사용하되, 여러 모델이 동의했다는 이유만으로 정답으로 확정하지 않습니다.

07 / 무엇이 바뀌고 무엇이 남나

큰 변경은 서버의 읽기 방식입니다.

항목현재제안
프론트 신경망추천 네모는 픽셀 규칙별도 모델 추가 없이 유지
CV 데이터 활용소수 학습지로 조정된 규칙개발용 문제에서 실패 유형별 조정·회귀 확인
문제 문맥별도로 글을 읽어 도형 결과에 붙임문제 문장과 그림을 함께 보고 판별·추출
AI 호출 구조도형별 해석 + 문제 글 별도 읽기문제 단위 통합 호출 1회를 우선 시험
지원 판별프롬프트의 notSolid 지시 등지원 / 미지원 / 정보 부족과 보기 대응을 명시
응답 계약도형 요청마다 단일 ShapeScene여러 도형·부분 지원·판별 이유의 설계 필요
3D 생성기하 코드 + three.js기존 구성 활용
정답 은행실행 중 동일 입력 캐시와 보관함 존재유사 문제 자동 재사용 은행은 이번 실험에서 보류

싸게 호출하는 것보다, 정확히 끝내는 비용을 봅니다.

AI 입력·출력 비용 + 재시도 비용 + 서버 비용을 기록합니다. 사용자 수정·보완에 걸린 시간은 따로 측정합니다.

미지원 문제를 잘못 받아들이는 비율, 지원 문제를 거절하는 비율, 판단 보류율, 최종 3D 정확도를 함께 봅니다.

전부 거절하거나 보류해서 오류율만 낮추는 방식은 성공이 아닙니다. 3D와 사진 처리가 함께 실행되는 휴대폰의 메모리·반응성도 채택 조건입니다.

아직 확정되지 않은 것
Flash-Lite가 모든 구조를 충분히 정확히 읽는지, 통합 호출이 실제로 더 빠르고 싼지, 4개 예시가 유리한지는 실험 전입니다. 이 HTML은 비교 계획이며 서비스 코드나 API를 바꾸지 않았습니다.
