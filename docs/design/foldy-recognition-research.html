01 / 무엇을 연구하는가

도형 탐지 성능만으로 결정할 수 없습니다.

사용자는 여러 문제가 담긴 사진에서 궁금한 문제를 고릅니다. Foldy는 그 문제의 의미와 표현 가능성을 판단하고, 필요한 그림을 가져와야 합니다. 문제를 잘못 이해한 채 멋진 3D를 그리는 것이 가장 먼저 줄여야 할 오류입니다.

제품의 경계

무엇을 받아들일까?

직육면체·정육면체만? 다른 다면체도? 올바르지 않은 전개도는? 평면 종이접기는?

결정 결과: 지원 / 미지원 / 판단 보류 사례표.

판별의 근거

무엇을 보고 구분할까?

그림의 생김새와 문제 문장을 함께 봅니다. “접는다”는 단어 하나로 전개도와 종이접기를 구별할 수 없습니다.

결정 결과: 문맥 입력과 보류·확인 경로.

실행의 비용

어디에서 처리할까?

브라우저에는 3D와 사진 처리가 이미 있습니다. 별도 모델의 메모리·초기화·운영비를 포함해 비교합니다.

결정 결과: 기존 서버 인식 활용 또는 추가 모델 도입.

이전 검토에서 바뀐 점
“20~30개 문제로 네모 탐지기부터 비교”를 첫 단계로 두지 않습니다. 같은 규모의 작은 표본을 쓰되, 먼저 문제 종류와 지원 여부를 사람이 정하고 현재 인식기의 잘못된 수용·거절을 확인합니다.
02 / 지원 범위의 정의

그릴 수 있는 도형과
사진에서 읽을 수 있는 문제는 다릅니다.

현재 구현

뷰어가 표현하는 범위

직육면체 외에도 여러 정다면체·각기둥·각뿔·곡면 도형을 그리는 코드가 있습니다. ShapeScene의 도형 종류와 매개변수에 맞춰 구성합니다.

외부 3D 파일을 찾아 인용하거나, 모르는 형상을 임의로 새로 모델링하는 구조는 아닙니다.

현재 구현

사진 인식의 범위

현재 비전 프롬프트는 직육면체·정육면체의 겨냥도와 전개도 중심입니다. 평면 도형·종이접기 등은 notSolid로 거르도록 지시합니다.

지시가 있다고 정확한 판별이 보장되지는 않습니다. 다른 다면체를 뷰어가 그릴 수 있다는 사실만으로 사진 인식까지 지원한다고 안내하면 안 됩니다.

문제 유형초기 지원 정책 제안판별 시 주의할 점
직육면체·정육면체 겨냥도지원 후보치수·라벨·그릴 선이 현재 계약으로 표현 가능한지 확인
직육면체·정육면체 전개도지원 후보전개도 배치를 원본 그대로 읽어야 함
“전개도가 아닌 것”을 고르는 보기지원 후보에 포함잘못된 배치도 학습 대상. 올바른 입체로 강제 보정하지 않음
평면 사각형 종이접기현재 자동 3D 인식에서는 미지원접힌 그림이 입체처럼 보여도 문제의 대상은 평면 종이일 수 있음
그 밖의 다면체·곡면 도형사진 인식 범위 확대 전까지 구분 안내입체도형이 맞지만 현재 읽기 범위 밖일 수 있음
문장이 잘렸거나 유형이 혼합된 문제판단 보류 또는 부분 처리 확인모두 거절하거나 전부 지원한다고 판단하지 않음

위 표는 합의를 위한 초안입니다. “지원 후보”는 현 인식 정확도가 검증됐다는 뜻이 아닙니다. 입체도형 여부, 현재 지원 범위, 표현 가능성을 별도로 확인해야 합니다.

두 가지 질문을 분리합니다.
① 이 문제는 우리가 다루는 학습 활동인가? ② 이 전개도가 실제로 닫힌 입체가 되는가?
②의 답이 “아니오”여도 ①은 “예”일 수 있습니다. 잘못된 전개도를 접어 보며 이유를 알아보는 활동이 그 예입니다.
03 / 문맥으로 구분하기

비슷한 사각형도 문장이 바뀌면 역할이 달라집니다.

아래 문제 문장을 바꿔 보세요. 도형의 윤곽만으로는 지원 여부를 확정하기 어렵다는 설명용 예시입니다. 실제 분류 모델을 실행하지 않습니다.

모식도입니다. 첫 세 예시는 같은 사각형 윤곽을 서로 다른 문맥에서 해석합니다.

지원 후보

직육면체의 한 면 ABCD 위에 대각선 AC를 그었습니다.

그림은 사각형이지만 문맥은 입체도형의 한 면입니다. 전체 입체의 치수와 면 대응이 충분한지도 확인해야 합니다.

다음 행동: 문제 전체에서 입체 정보와 면의 관계를 확인한 뒤 지원 여부를 결정합니다.

어디 있나?

탐지: 도형·문장 영역의 네모. 현재 픽셀 규칙은 이 단계의 일부를 담당합니다.

무슨 문제인가?

의미 판별: 입체 전개도인지, 평면 종이접기인지, 범위 밖인지. 문장과 그림의 관계가 중요합니다.

어떻게 표현하나?

구조 해석: 치수·면 배치·라벨을 지원하는 데이터로 변환. 형식 검증만으로 내용의 정확성을 증명할 수는 없습니다.

도형이 여러 개면 문제 전체를 한 번에 거절하나요?

그렇게 단순화하면 안 됩니다. 하나의 문제에 지원 가능한 전개도와 다른 참고 그림이 함께 있을 수 있습니다. 문제 수준의 학습 활동을 판단하고, 각 보기의 역할·지원 여부를 구분해야 합니다. 일부만 표시한다면 어떤 보기를 다루는지 사용자가 알 수 있어야 합니다. 보기 번호와 도형의 대응도 평가 대상입니다.

04 / 프론트의 현실적인 비용

모델의 실행 위치부터 비교합니다.

“모델을 구축한다”는 말이 곧 “휴대폰에 모델을 넣는다”는 뜻은 아닙니다. 학습 비용과 서비스 실행 비용도 다릅니다. 현재 추천은 기존 서버 인식 과정에 문맥 판별을 포함할 수 있는지 먼저 검증하는 것입니다.

방식프론트 영향추가 비용·제약검토 순서
현재 규칙 + 기존 서버 인식새 모델 다운로드 없음문맥 판별·도형 해석의 정확도와 기존 대기기준선
기존 인식 호출에 지원 판별 통합결과 안내 UI 중심입력·출력 설계, 복잡해진 지시가 해석에 미치는 영향우선 검증
서버 탐지·분류 모델 추가모델을 브라우저에 싣지 않음서버 메모리·기동·동시성·운영비·왕복 시간현재 방식의 실패가 확인되면
브라우저 탐지·분류 모델 추가다운로드·초기화·CPU/GPU·메모리 증가 가능3D와 함께 작동할 때의 프레임·조작 반응기기 실측상 이득이 있을 때만
문서 탐지기는 의미 판별기의 대체물이 아닙니다.
“그림이 여기 있다”를 잘 찾는 모델이 “이것은 평면 종이접기 문제다”까지 판별한다고 가정하지 않습니다. PP-DocLayout·DocLayout-YOLO는 위치 탐지 후보이며, 문맥 판별은 별도 검증해야 합니다.
어떤 자원과 시간을 측정하나요?

기준 상태와 후보 상태에서 같은 사진·기기로 비교합니다. 최초 모델 다운로드·준비 시간, 준비 후 처리 시간, 사진 업로드부터 판정·3D까지의 전체 대기, 회전·접기 중 프레임과 조작 반응, 메모리와 탭 종료 여부를 기록합니다. 서버 방식은 동시 요청·기동 지연·요청당 비용도 포함합니다. 기기·브라우저별 측정 가능한 항목과 한계를 함께 적습니다.

모델이 없는 기존 방식도 큰 사진 디코딩·3D 텍스처로 메모리가 늘 수 있으므로 추가 모델에 의한 증가분을 구분합니다. 현재 15~20초 수준의 인식 대기 기록은 특정 팀 테스트 환경의 과거 측정이며, 새 구조의 성능 보장값이 아닙니다.

05 / 사용자 경험과 필터

지원 범위를 안내하고, 입력 뒤에도 확인합니다.

학생에게 전개도와 평면 종이접기의 차이를 완벽히 알고 올리라고 요구하기는 어렵습니다. 안내는 입력을 돕고, 시스템 판별은 잘못된 결과를 줄이는 역할입니다.

입력 전 안내 예시

“정육면체·직육면체 그림이나 전개도가 있는 문제를 골라 주세요.”

“문제 문장과 그림이 함께 들어오게 감싸 주세요. 다른 문제는 아직 읽기 어려울 수 있어요.”

사용자가 문제를 선택

사진에서 문장과 필요한 보기가 포함된 영역을 고릅니다. 여러 페이지 업로드는 별도 확장 범위입니다.

그림 위치와 문맥 확보

추천 네모를 쓰더라도 문제 전체와 각 보기의 관계를 유지합니다. 문맥을 잃는 작은 조각만 보내지 않습니다.

지원 판별 + 구조 해석

기존 서버 호출에서 함께 수행할 수 있는지 검증합니다. 잘못된 전개도도 그대로 표현하는 원칙을 지킵니다.

지원 가능

검증 후 3D로

현재 범위에 맞고 표현 정보가 충분합니다. 데이터 구조와 사진 대응을 검사한 뒤 표시합니다.

JSON 형식 통과 = 사진 내용의 정답이라는 뜻은 아닙니다.

미지원

이유와 범위 안내

“이 문제는 평면 종이를 접는 문제예요. 현재는 정육면체·직육면체의 전개도를 볼 수 있어요.”

비슷한 입체를 임의로 만들어 대신 보여주지 않습니다.

판단 보류

정보 보완 요청

“문제 문장이 잘렸어요. 글과 그림이 함께 들어오게 범위를 넓혀 주세요.”

사용자 확인 뒤에도 표현 정보가 부족하면 3D를 확정하지 않습니다.

현재 구현에서 점검할 지점
여러 도형을 읽을 때 문제 칸 이미지는 첫 번째 요청에만 전달하고, 첫 결과의 문제 글을 다른 결과에 붙입니다. 이후에 글을 붙이는 것만으로 다른 도형의 판별 당시 문맥 부족이 해결되지는 않습니다. 모든 도형이 필요한 문맥을 활용하도록 하는 방법을 실험해야 합니다.
구현 전에 바뀌어야 하는 계약은?

지원 / 미지원 / 판단 보류의 응답 형태, 부분 지원과 보기 번호 대응, 미지원 이유, 정보 부족 시 안내 경로를 먼저 정의해야 합니다. 현재 단일 ShapeScene 응답과 notSolid 처리에서 무엇을 바꿀지 문서·이슈로 합의하고 구현합니다. 이 HTML은 제안서이며 API나 ShapeScene을 변경하지 않습니다.

06 / 다시 정렬한 검증 계획

첫 실험은 “무엇을 잘못 받아들이는가”입니다.

20~30개 문제로 경계 사례를 탐색합니다. 이 작은 표본은 문제 발견용이며 운영 정확도를 보장하는 시험이 아닙니다. 처음부터 100장 학습·정답 은행·전체 교차 심사를 진행하지 않습니다.

1

사람이 지원 경계부터 정의

겨냥도, 정상 전개도, 잘못된 전개도, 평면 종이접기, 지원 밖 입체, 문맥 부족, 여러 유형이 섞인 문제를 고릅니다. 각 문제와 보기마다 지원 / 미지원 / 보류, 이유, 필요한 정보를 기록합니다.

결정: 사람이 경계에 합의하지 못하는 사례는 모델의 정답으로 고정하지 않습니다.

2

기존 인식기의 문맥 판별 평가

현재 방식과 문맥을 충분히 전달한 방식을 비교합니다. 모델·촬영 입력·실행 조건을 기록합니다. 판별을 함께 요청했을 때 지원 문제의 구조 해석이 나빠지지 않는지도 확인합니다.

결정: 별도 모델 없이 목표에 도달하면 추가 모델 도입을 생략합니다.

3

실패한 단계를 분리

문제 글 누락, 도형 누락, 보기 대응 오류, 유형 오판, 지원 범위 혼동, 치수·라벨 해석 오류를 나눕니다. 사람이 정확히 자른 입력도 함께 넣어 탐지 실패와 해석 실패를 구별합니다.

결정: 위치가 문제일 때 탐지기를, 문맥이 문제일 때 판별·입력 구성을 개선합니다.

4

필요한 후보만 서버에서 비교

위치 탐지 실패가 크면 문서 탐지기를 먼저 학습 없이 시험합니다. 문맥 판별 실패가 크면 판별 방법을 별도로 비교합니다. 사전학습 모델이 우리 도메인에 부족하고 개선 가능성이 보일 때만 약 100장 학습을 검토합니다.

결정: 작은 모델이라는 이름보다 최종 결과와 전체 비용으로 채택합니다.

5

새 교재와 목표 휴대폰에서 확인

교재·원본 문제 묶음으로 학습/검증/시험을 분리합니다. 3D 회전·접기와 사진 처리를 실제로 사용하며 추가 지연과 메모리를 측정합니다. 서버 방식은 동시 요청과 운영비도 비교합니다.

결정: 경계 판별, 지원 문제의 인식 성공, 사용자 수정 부담, 실행 비용을 함께 보고 최종 선택합니다.

평가 지표분모·의미사용 목적
미지원 문제의 잘못된 수용률사람이 미지원으로 정한 문제 중 지원 판정 비율그럴듯한 잘못된 3D로 이어질 수 있는 최우선 오류
지원 문제의 잘못된 거절률지원 정답 중 미지원 판정 비율쓸 수 있는 문제를 불필요하게 막는지
판단 보류율·보완 성공률보류한 요청 수와 보완 뒤 해결된 수모두 보류해서 오류율만 낮추는 상황 방지
지원 판정 후 결과 정확도받아들인 문제에서 도형·치수·배치·라벨의 오류통과만 하고 내용이 틀리는 문제 확인
무수정 성공률·완료 시간수정·재시도·보완 요청을 포함한 사용자 흐름실제 사용 부담
기기·서버 비용초기화·전체 대기·메모리·조작 반응·운영비기술적으로 돌아가는 것과 제품으로 적합한 것 구별
단일 정확도 숫자는 부족합니다.
전부 거절하면 미지원 수용은 줄지만 서비스는 쓸 수 없습니다. 전부 보류해도 마찬가지입니다. 유형별 성공·실패 건수와 분모, 보류율을 함께 보고합니다. 판별 임곗값과 채택 기준은 개발 표본에서 정한 뒤 최종 시험 전에 고정합니다.
정답 은행과 증류는 이 계획에서 어디에 있나요?

지금 필요한 것: 문제 종류·지원 여부·실패 원인을 담은 검증 데이터입니다. 기존 기록 모드는 이를 모으는 데 활용합니다. 사용자 삭제나 “직접 고치기” 행동을 정답으로 단정하지 않습니다.

나중에 판단할 것: 검증된 ShapeScene을 새 요청에 자동 재사용하는 정답 은행입니다. 반복 문제의 실제 비율과 숫자·라벨만 다른 문제를 혼동할 위험을 별도로 측정해야 합니다. 은행이 있어도 처음 보는 미지원 문제를 구분하는 문제는 남습니다.

#161의 기록 정리·규칙 조정과 교사 모델로 학생 모델을 학습시키는 지식 증류는 다릅니다. 이번 연구는 둘 중 어느 투자가 필요한지 판단하기 위한 선행 검토입니다.

07 / 현재 권고와 미정 사항

프론트를 더 무겁게 만들기 전에
기존 인식 경로의 한계를 확인합니다.

우선 검증할 방향

입력 전에 실제 지원 범위를 안내합니다.
문제 문장과 그림을 함께 보고 지원 여부를 판별합니다.
기존 서버 호출에서 판별과 구조 해석을 함께 수행할 수 있는지 확인합니다.
지원 / 미지원 / 판단 보류를 구분하고, 일부 보기만 처리할 때는 명시합니다.
실패 원인이 확인된 뒤에만 별도 모델과 정답 은행에 투자합니다.

성능이 입증된 최종 아키텍처가 아니라 다음 실험의 우선안입니다. 브라우저 모델이 불가능하다는 결론도 아닙니다.

08 / 근거와 적용 한계

문헌이 뒷받침하는 것과 아직 검증할 것

아래 자료는 기존 검토에서 확인한 위치 탐지·소량 학습·배포 후보의 근거입니다. 한국어 학습지의 평면 접기와 입체 전개도를 정확히 판별한다는 직접 증거는 아닙니다. 그 부분은 Foldy 표본으로 검증해야 합니다.

PP-DocLayout · 2025

문서 영역 탐지를 위한 여러 크기의 모델. S 모델의 논문상 CPU 14.5ms는 경량 후보를 시험할 근거이며, Foldy 기기 속도를 보장하지 않습니다.

DocLayout-YOLO · 2024

다양한 합성 문서 사전학습과 다중 크기 요소 탐지. 문서에 특화된 사전학습 모델을 비교 후보로 삼는 근거입니다.

Frustratingly Simple Few-Shot Object Detection · 2020

기존 탐지기의 일부 층을 소량 예제로 미세조정하는 접근. 소량 학습의 가능성과 표본 선택에 따른 성능 편차를 함께 보여줍니다.

DocLayNet · 2022

다양한 문서 레이아웃의 주석 데이터셋. 특정 문서 유형에서 잘된 결과를 다른 교재로 일반화하면 안 되는 이유입니다.

Plane Geometry Diagram Parsing · 2022

기하 요소 추출과 관계 해석을 다루는 PGDPNet. 도형 위치 탐지와 내부 기하 구조 해석이 다른 난도의 작업임을 보여줍니다. 평면 기하 연구이며 Foldy 3D의 직접 대체물이 아닙니다.

Distilling the Knowledge in a Neural Network · 2015

교사 모델의 지식을 다른 모델로 옮기는 지식 증류. 프로젝트에서 쓰는 기록 정리·규칙 조정이라는 “증류”와 용어를 구분하는 근거입니다.

ONNX Runtime Web · 공식 문서

브라우저 내 모델 실행 경로. 모델 변환·연산 지원·기기 메모리를 확인한 뒤 사용할 수 있으며, 학습이 끝났다고 바로 휴대폰 실행이 보장되지는 않습니다.

Foldy 내부 구현·계획

추천 네모 코드 · ShapeScene 계약 · 추천 네모 실측 기록

#161 증류·정답 은행 · #162 교차 심사. 이 문서는 두 이슈의 구현 착수 전 검토안이며 이슈 상태를 바꾸지 않습니다.
